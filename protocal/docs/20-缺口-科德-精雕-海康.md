/KEDE/CNC/GNC62/Open/TCP   Close   STATUS   PROGRAM   LINE_NUMBER   PART_COUNT

### 1.1 设备侧报文（🟢 本地仿真抓取，2026-09）——科德的字节面齐了

现场交付包的 Go 网关（`hp2x_box200`）自己实现了 GNC62 协议。把它的
`/KEDE/CNC/GNC62/Open/TCP` 指向假机床（`ipAddress` + `port: 62937`），再逐项
POST `/KEDE/CNC/GNC62/<项>`，设备侧请求就原样落到手上（复现：
`tools/site-probe/gateway_probe.sh`）。

**协议是"一行一个 XML"**，`\n` 结尾；`uid` 是自增序号（每项 +1，重试用原号）：

| 项 | 设备侧请求 |
|---|---|
| `STATUS` | `<ncda><req>yes</req><uid>1</uid><var>ncstate</var></ncda>` |
| `PART_COUNT` | `<counter><req>yes</req><uid>2</uid><sub>get</sub></counter>` |
| `PROGRAM` | `<ncda><req>yes</req><uid>3</uid><var>prg</var></ncda>` |
| `LINE_NUMBER` | `<ncda><req>yes</req><uid>4</uid><var>block</var></ncda>` |
| `FEED_SPEED` | `<feed><req>yes</req><uid>5</uid></feed>` |
| `SPDL_SPEED` | `<spindle><req>yes</req><uid>6</uid></spindle>` |
| `FEED_OVERRIDE` | `<feed><req>yes</req><uid>7</uid></feed>` |
| `SPDL_OVERRIDE` | `<spindle><req>yes</req><uid>8</uid></spindle>` |
| `RAPID_OVERRIDE` | `<feed><req>yes</req><uid>9</uid></feed>` |
| `AXIS_ACT_POSITION` | `<axes><req>yes</req><uid>10</uid><sub>pos</sub></axes>` |
| `TOOL_PARAM` | `<record><req>yes</req><uid>11</uid><sub>tool</sub><pos>0</pos></record>` |
| `WARNING` | `<alarm><req>yes</req><uid>12</uid></alarm>` |

**应答的根元素**从网关的报错里直接读出来了（它按根元素分派）：
`<ncda>` / `<counter>` / `<feed>` / `<spindle>` / `<axes>` / `<record>` /
`<alarm>`——"expected element type `<counter>` but have `<ncda>`" 就是它给的。
`<ncda>` 用 `<var>` 点名变量（`ncstate` / `prg` / `block`），其余按根元素语义
取值；应答里的 `req` 取值（`yes`/`no`）与 `<val>` 的具体形状还用同一套办法迭代
一次即可（`gateway_probe.sh <应答文本>`）。

### 1.2 应答：已经能让网关"收下"了（🟢 2026-09）

继续用"让网关自己报错"的办法（新工具 `tools/site-probe/kede_reply_probe.sh`，
`mock.py` 支持 `XSUB:`——按收到的请求回填 `{uid}` / `{reqflip}`）。三条结论：

1. **uid 必须原样回填**：不回或填错 → `inconsistent UID`；而且 `<uid>` 必须是
   **子元素**（写成属性 `<counter uid="…">` 同样报 `inconsistent UID`）。
2. **最小可收下的应答**（网关返回 `code:0`）：

   ```
   <counter><req>no</req><uid>{请求里的 uid}</uid><sub>get</sub></counter>
   ```

   `ncda` 类同形：`<ncda><req>no</req><uid>…</uid><var>ncstate</var></ncda>`。
   也就是说**离线仿真器现在能把整条链路跑通**（只是数值为 0）。
3. **取值元素：`<actual>`（已验证）**。做法是"把网关里那 100 多个字段名一次性
   塞进应答、每个配一个不同数字"——回来的数字就能反查出它读的是哪个字段：
   `<counter>` 回了 **9**，而 9 号字段是 `actual`；再用 `<actual>77</actual>`
   复验，网关回的正是 **77**。所以计数的完整应答是：

   ```xml
   <counter><req>no</req><uid>{请求里的 uid}</uid><sub>get</sub>
            <actual>77</actual></counter>
   ```

4. **字符串类（`<ncda>`，如 `STATUS`）取的是整数**：把 `<ncstate>free</ncstate>`
   发给它，网关直接回 `strconv.ParseInt: parsing "free": invalid syntax`——
   说明这两个字段是整型，机床给的是**状态码**而不是文字（`ncstate`、`status`
   两个字段都是整型，哪个出现就会去解析哪个）。

**网关的全部 XML 标签（159 个，🟢 从 Go 二进制的 `xml:"…"` 结构体标签抄出）**：

```
外层: ncda counter feed spindle axes record alarm
字段: ncstate prg block over1..over6 act1..act6 actf0 ax1..ax32
      position1..6 preset1..6 bar1..bar6 state1..state32 v1..v9
      nmb no max ret info status mode mmode amode test tool unit pos
      sub uid req var switch bsupr backw hrel inauto manrtcp blksel debugmode
      prio tm localtime remainingdertime proctime0/1/proc/start
      actual preset over act bar m01 ver time auto st
```

这张表同时是**其它 XML 类模块**的取值依据（网关里 XML 只有这一套词表）。
取值元素定下来之后，科德这条链就完全闭环了。

**现场协议实现的能力面（Go 符号 `hp2x/protocols/kede/cnc/gnc62`）**：

| 量 | 方法 | 请求族（= GNC62 的命令分类） |
|---|---|---|
| 状态 | `STATUS` | `NewCommonRequest` |
| 程序 | `PROGRAM` | `NewNcdaRequest` |
| 行号 | `LINE_NUMBER` | `NewNcdaRequest` |
| 加工计数 | `PART_COUNT` | `NewCounterRequest` |
| 进给 | `FEED_SPEED` `FEED_OVERRIDE` | `NewFeedRequest` |
| 主轴 | `SPDL_SPEED` `SPDL_OVERRIDE` | `NewSpindleRequest` |
| 轴坐标 | `AXIS_ACT_POSITION` | `NewAxesRequest` |
| 刀具参数 | `TOOL_PARAM` | `NewCommonRequest` |
| 报警 | `WARNING` | `NewAlarmRequest` |

另有 `getUid`（会话号/流水号，和 MC 的 serial、SYNTEC 的 uSerial 同性质）与
`NewRecordRequest`（记录类）。**结论**：GNC62 是"**按数据族分命令**"的私有协议，
八个 `New*Request` 就是它的请求构造器；**每个族的字节布局仍需一次抓包**。

**现场端点**：`/JINGDIAO/CNC/Open/TCP`、`Bind`、`Close`、`STATUS`、`LINE_NUMBER`、

映射的模型项与 SYNTEC 那一组完全一致（见 28 册 §5.4），并且**多一个 `Bind`**——

**已知线索**：
- 存在《精雕 50 系统联网监控开发包及说明 V20180105.zip》（CSDN 下载，**需积分**）
- 端口 89 —— 非标准端口，说明是私有协议

### 2.1 设备侧报文（🟢 本地仿真抓取，2026-09）

同一套办法（跑现场 Go 网关 + 假机床）也适用于精雕，但要注意**它会自己扫端口**：
给 `Open/TCP` 的 `port` 只当起点，实测它依次拨 7080、7081…（默认落在 **7080**，
不是扫描表里的 89）。假机床把 7080–7090 全接住，连接就成功，随后每项一帧：

**24 字节定长**，前 12 字节固定 `05 00 00 03 10 00 00 00 18 00 00 00`，
接下来 4 字节是**自增序号**（从 02 开始），最后 2 字节是数据项代码：

| 项 | 序号 | 帧尾 |
|---|---|---|
| `STATUS` | 02 | `02 00` |
| `PART_COUNT` | 03 | `0e 00` |
| `PROGRAM` | 04 | `03 00` |
| `LINE_NUMBER` | 05 | `03 00` |
| `FEED_SPEED` | 06 | `03 00` |
| `SPDL_SPEED` | 07 | `03 00` |
| `FEED_OVERRIDE` | 08 | `0f 00` |
| `SPDL_OVERRIDE` | 09 | `0f 00` |
| `WARNING` | 0a | `3b 00` |

例（`STATUS`，24 字节）：

```
05 00 00 03 10 00 00 00 18 00 00 00 02 00 00 00 00 00 00 00 00 00 02 00
```

**注意**：`PROGRAM` / `LINE_NUMBER` / `FEED_SPEED` / `SPDL_SPEED` 四项发出去的帧
**逐字节相同**（只差序号）——说明精雕是"按代码读一整块状态，客户端自己从回包里
取字段"。所以这一家的最后一格不是请求，而是**回包布局**：请求侧已经齐了，
把回包构造对就能把四个字段拆出来（`gateway_probe.sh <应答hex>` 迭代）。

**回包布局**见 §2.2（已解到"24 字节一包的链"，多数项已经闭环）。

### 2.2 回包：24 字节一包的链（🟢 2026-09 第三轮）

反汇编 `(*CJDMachMon).RPCRequest`（`0x620dec-0x6216a0`，它一个函数包办收发与拆包）
＋假机床实测（`tools/site-probe/jingdiao_reply_probe2.sh` … `probe7.sh`）：

**回包不是"一帧"，而是 24 字节一包的链**，每包的字段与请求同构：

| 偏移 | 含义 | 必须值 |
|---|---|---|
| 2 | **包类型** | `0x02`（否则 `[response(0x02)] packet type error: %d`） |
| 3 | 标志位 | **bit1（0x02）= "最后一包"**：只有它置位驱动才收手；bit1 清 0 时驱动继续等下一包（表现为 `short read 0/24 bytes`） |
| 8..9 | u16 LE，本包"含头长度" | 包1 写 `24`（=0x18）；包2 写 `24 + 载荷长` |
| 12..15 | 序号 | 回声请求里的序号 |
| 22..23 | 项码 | 回声请求里的项码 |

**载荷跟在第 2 包之后**（不是第 1 包之后）。拿 `PART_COUNT` 说：

```
包1  05 00 02 01 10 00 00 00 18 00 00 00 <序号> 00 00 00 00 00 00 0e 00   （回声请求，只把 [2] 改成 02、[3] 改成 01）
包2  00 00 02 02 00 00 00 00 1c 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  （[2]=02、[3]=0x02、[8..9]=24+4）
载荷 d2 04 00 00                                                          （int32 = 1234）
```

按这套造帧，`/JINGDIAO/CNC/PART_COUNT` 回 **1234**，换 7 / −1 也如实回（−1 → 4294967295）
✅。**取值偏移**用"载荷第 k 字节 = k"扫出来（返回值的字节序直接指认偏移）：

| 端点 | 请求码 | 取值 | 实测返回值（载荷第 k 字节 = k） |
|---|---|---|---|
| `PART_COUNT` | 14 | 载荷 **[0..3]** u32 | 50462976 = `0x03020100` ✅ |
| `FEED_OVERRIDE` | 15 | 载荷 **[4..7]** u32 | 117835012 = `0x07060504` ✅ |
| `SPDL_OVERRIDE` | 15 | 载荷 **[0..3]** u32 | 50462976 ✅ |
| `SPDL_SPEED` | 3 | 载荷 **[8..11]** u32 | 185207048 = `0x0B0A0908` ✅ |
| `LINE_NUMBER` | 3 | 载荷 **[20..23]** u32 | 387323156 = `0x17161514` ✅ |
| `PROGRAM` | 3 | 载荷 **[24..27]** u32 → **当数字再转成字符串** | `'454695192'`（= `0x1B1A1918`）✅ |

> 这也解释了 §2.1 的怪现象：`PROGRAM`/`LINE_NUMBER`/`FEED_SPEED`/`SPDL_SPEED`
> 四项请求逐字节相同——它们同属 `GetBasicModalInfo`（码 3），一次读回一整块状态，
> 客户端自己按偏移拆字段。

**最后三项也闭环了**（`jingdiao_reply_probe8.sh` / `probe9.sh`）：

| 端点 | 载荷格式 | 实测 |
|---|---|---|
| `FEED_SPEED` | **[4..7] = float32**（`GetBasicModalInfo` 里确实用到 float32 类型 `0x7446e8`） | 放 `12.5` → 回 `12.5` ✅（逐档扫过 0/4/8/…/32，只有 4 命中） |
| `STATUS` | **[0..3] = u32 状态枚举** | `0`/`3` → `'free'`、`1` → `'running'`、`2` → `'holding'`、≥4 → `'unknown'` ✅ |
| `WARNING` | **载荷 = u32 报警号数组，遇到 0 结束**；载荷长度给 **2500** 字节 | 全 0 → `[]`；`[0..3]=2` → 1 条；`[0..3]=1,[4..7]=A,[8..11]=B` → 3 条 ✅ |

> `WARNING` 的 `text` 恒为空串——文本不是从报文里来的，是驱动**按报警号查自己的**
> 表（表里没有的号就是空串）。

九项至此全部可仿真（请求 + 应答），只剩 `Bind`/`GetResponse` 这两个非数据端点没扫。

**攻坚路径**：
1. CSDN 积分下载开发包（最直接，几十积分）

3. 现场抓包反推

## 3. 海康威视相机（HCNetSDK）

| 项 | 值 |

| 端口 | **8000**（SDK 默认） |

**现场形态**：`libcamera.so` 里是一个 C++ 类（`CAMERA::CAMERA(spdlog::logger*, int)`、
`CAMERA::getFeature(vector<float>&, string, int, ...)`、`CAMERA::getCV2(string, string)`），
即"取特征量 + 取一帧图像（OpenCV Mat）"。它**不导出**插件 ABI（`create/call/destroy`），
所以相机是**给别的模块调用**的能力，不是独立协议插件。
要复刻这条链路仍需要相机 SDK 的头文件（`getFeature` 的入参语义只有调用方能给全）。

**攻坚路径**：
1. **海康开放平台注册**（open.hikvision.com）→ 下载 HCNetSDK（免费，需实名认证）
2. SDK 形态：`HCNetSDK.dll`/`.so` + 头文件（结构体 + 函数式 API）
3. 常用能力：`NET_DVR_Login_V40` → `NET_DVR_GetDVRConfig` / 抓图 / 云台控制

**注意**：本机网络下 open.hikvision.com 不可达 —— 需在有外网的机器注册下载。

## 5. 通用攻坚方法论（适用于任何缺口协议）

```
① 优先找官方 SDK/DLL → 抽导出表（pefile/dnfile/readelf）→ 得函数名
② 无 SDK → 找现成开源实现（PyPI/GitHub，注意网络通道）
③ 无任何资料 → 现场抓包（tcpdump/Wireshark）→ 报文聚类 → 逐步对应语义
   技巧：
     - 改变机床状态（启动/停止/换程序）同时抓包，比对报文差异定位字段
     - 高频报文 = 坐标/速度；低频 = 状态/报警；事件触发 = 报警
     - 文本协议先找 ASCII 可读串（程序名/路径）；二进制先找长度字段规律
④ 交叉验证：同一语义在其它厂商协议里的实现方式（商业库 49 个报文类可作对照）
⑤ 落地：先只读，验证稳定后再开写
```
