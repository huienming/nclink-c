# 29 · 现场交付包的模型与驱动定义（`cfg` + 插件符号）

> 用途：回答"读 `app1/`（现场 iNC-BOX-200）能不能把缺的驱动逆出来"。
>
> **结论：数据面已经齐了。** `cfg/models/<品牌>.json`（数据项）、
> `cfg/driver_defs/<品牌>_driver.json`（连接与分派）、`lua/lua_mod/*.lua`
> （模型项 → 端点 + 规整）、`lib*.so` 的 `.dynsym`（插件方法签名与项键）
> 四份叠起来，就是现场每个驱动的**定义**——逐项、逐方法、带端口和参数。
> 剩下只有一样：自研实现的**线协议字节/URL**（GSK / KEDE / Mitsubishi-HTTP 这类
> 插件自己发 HTTP、不走供应商 SDK 的），仍需一次抓包；而这一次抓包也能在本地做
> （qemu 跑 ARM 插件 + 假机器，见 §6），不必等现场。
>
> 证据分级：🟢 现场二进制/配置实测。

## 1 链路：谁定义什么

```
cfg/models/<品牌>.json          NC-Link 设备模型（数据项 + 采样通道）
cfg/driver_defs/<品牌>_driver.json  驱动定义（模块、IP/端口/超时、路径分派、后台任务）
lua/lua_mod/<品牌>_mod.lua      模型项 → 网关端点 + 数据规整
app1/hp2x/hp2x_box200           Go/GoFrame 设备协议网关（:33123）
app1/nclink-service + lib*.so   插件：厂商协议实现（C++，ELF32 ARM）
libfwlib32.so / libHsc3Api.so / libCommApi.so  供应商 SDK
```

| 现场文件 | 里面是什么 | 我们这边的对应物 |
|---|---|---|
| `cfg/models/<品牌>.json` | `dataItems[].type`（`STATUS`/`FEED_SPEED`/`PART_COUNT`/`POSITION`/`SPEED`/`CURRENT`/`LOAD`/`PROGRAM`/`LINE_NUMBER`/`WARNING`/`VARIABLE@…`）、`components[].configs[]`（`TOOL_PARAM`/`COORDINATE`/`FILE`/`CONSOLE`）、`SAMPLE_CHANNEL` | `ncl_adapter` 的模型（`model.json` 或按点位表生成） |
| `cfg/driver_defs/<品牌>_driver.json` | `connections[]`（`module` + `ipAddress`/`port`/`timeout`）、`drivers`（`/`、`/CONTROLLER/FILE` → client）、`tasks[]`（Lua 脚本 + 周期） | `conf/driver/*.json`：链路 + 点位表 |
| `lua/lua_mod/<品牌>_mod.lua` | `["get_value@/STATUS"] = {url=…, data_process=…}`：模型项 → 网关端点，外加规整（取整、数组标记、共享状态） | 点位表 + 规整规则（如 KND 那条 ×100 / `100%02d`） |
| `lib<品牌>.so` | 插件本体：`BaseNCMod` 派生类，**strong 覆盖**它支持的项；项键（`/GSK/CNC/STATUS` 之类）是字符串字面量 | 我们的 driver（`ncl_driver_ops`） |
| `libfwlib32.so` / `libHsc3Api.so` / `libCommApi.so` | 供应商 SDK（FANUC FOCAS、华数 Hsc3、华数的 asio 传输层） | 无——这类协议可以直接调 SDK |

## 2 提取方法（可复现）

`.so` 全部是 **ELF32 ARM，`.symtab` 与 `.debug_*` 都被 strip 掉了**，但
**`.dynsym` 还在**：类名、方法名、参数类型（C++ 修饰名）一个字没少。

```sh
docker run --rm -v <现场包>:/svc:ro -v $PWD:/out gcc:13 sh -c '
  for f in /svc/lib*.so; do
    b=$(basename $f)
    # 该插件真正实现的方法（strong）：T = 本插件定义，W = 继承 BaseNCMod 的默认实现
    nm -D --defined-only $f | c++filt | awk "\$2==\"T\"" | sort -u > /out/$b.methods
    nm -D -u $f | c++filt | awk "{print \$2}" | sort -u > /out/$b.imports   # 依赖的 SDK
    strings -n 6 $f > /out/$b.strings                                       # 项键与错误文本
  done'
```

三条判读规则：

1. **`T`（strong）= 插件支持的项**；`W`（weak）= 从 `BaseNCMod`（`libbase.so`）
   继承的默认实现，即"声明了但这家不支持"。所以"支持面"= strong 集合。
2. **`imports` 里的厂商函数**说明这家是"调 SDK"还是"自己实现"：
   `libfocas.so` 导入 29 个 `cnc_*`（FOCAS SDK），其余插件只导入通用库。
3. **`strings` 里的 `/品牌/…` 字面量**就是该插件认的项键，跟 Lua 里的 `url` 一一对上。

### 4.1 FOCAS：为什么"不用逆协议" 🟢

`libfocas.so` 导入的 29 个 `cnc_*` 就是这家用到的 FOCAS 调用：

cnc_rdparam cnc_rdtofs cnc_rdtofsinfo cnc_rdmacro cnc_rdalmmsg2 cnc_rdlife

## 6 本地仿真抓包：已经在跑，战绩与卡点

**这条路走通了**：现场包里的二进制全是 **ELF32 ARM hard-float**（Go 网关、宿主、
插件都是），Docker Desktop 自带 `binfmt`，加一个 `--platform linux/arm/v7` 就能在
本机跑起来；再把 `ipAddress` 指向我们自己的"假机床"，设备侧报文就归我们了。
工具与复现命令在 [`tools/site-probe/`](../tools/site-probe/README.md)：

```sh
cd tools/site-probe && docker build --platform linux/arm/v7 -t ncl-arm-probe .
docker run --rm --platform linux/arm/v7 \
    -v <现场包>/app1/nclink-service:/svc:ro -v $PWD:/work \
    ncl-arm-probe sh /work/focas_run.sh
```

### 6.1 FOCAS2 握手 🟢 已抓到

`libfwlib32.so` 的 `cnc_allclibhndl3("127.0.0.1", 8193, 3)` 对假机床依次发
（两次 TCP 连接、四条消息）：

```
a0 a0 a0 a0 00 01 01 01 00 02 00 01     # 12 字节，第一条连接
a0 a0 a0 a0 00 01 01 01 00 02 00 02     # 12 字节，第二条连接（计数器 +1）
a0 a0 a0 a0 00 01 21 01 00 00           # 10 字节
a0 a0 a0 a0 00 01 02 01 00 00           # 10 字节
```

没有应答时返回 **-16（EW_SOCKET）** 并重试一次。要往下拿数据调用
（`cnc_statinfo` / `cnc_rdparam` / `cnc_rdaxisdata` …）得先把这四条回应答对；
应答只有两种来源：一台真 FANUC 抓一次，或按 Fwlib32 手册把应答字段补全。

### 6.2 插件 ABI 🟢 已解出

插件导出 4 个未修饰的 C 入口（`nm -D`）：

```c
void *create(nlohmann::json *params, spdlog::logger *logger);
int   call(void *instance, int op /*OperationType*/, const char *method,
           nlohmann::json *request, nlohmann::json *response,
           nlohmann::json *extra);
void  destroy(void *instance);
const char *get_version(void);
```

`call` 转发到的 C++ 虚函数在 `libbase.so` 里，修饰名是
`_ZN7BaseMod4callESs13OperationTypePN8nlohmann10basic_jsonISt3map…ES9_S9_`，
即 `BaseMod::call(std::string method, OperationType op, json*, json*, json*)`。
（**C 侧参数顺序是"实例、操作类型、方法名、请求 json、响应 json、附加 json"**；
第一版 harness 按 `(实例, 方法名, 参数文本, out)` 传，把 `const char*` 当枚举、
把参数文本当 json 解引用，直接段错误。）

三条硬约束（🟢 导入表/反汇编）：

1. **旧 string ABI**：插件导入的是 `_ZNSsC1EPKcRKSaIcE`（老 ABI 的 `std::string`），
   不是 `_ZNSt7__cxx1112basic_string…`；harness 必须
   `-D_GLIBCXX_USE_CXX11_ABI=0`，否则跨边界写坏堆（`free(): invalid pointer`）。
2. **自带第三方库**：HTTP 是 **cpp-httplib**（`httplib::Client::set_connection_timeout`
   等），日志是 **spdlog**（`spdlog::logger::debug<const char*&, const char*&>(
   fmt::v8::basic_format_string<…>)`），json 是 **nlohmann**，但它的 map 比较器是
   `std::less<std::string>`（修饰名 `St4lessISsE`），不是 3.11+ 的 `std::less<void>`。
3. **加载顺序**：`libstdc++.so.6` → `libbase64.so` → `libLogApi.so`
   （+`libboost_thread.so`）→ `libbase.so` → 具体插件。现场这些 `.so` 是 C++，但
   **NEEDED 里没有 libstdc++**，平时是宿主 `nclink-service` 把它拉起来的。

logger 可以造假：插件只拿它打日志，一个全零、虚表全是空函数的对象就够
（`plugin_drive.cpp` 的 `fake_logger_make()`）——用它可以一路走到
`ctor -> 0x4152bc`（实例真的造出来了）。

### 6.3 卡在哪（下一步）

现在能"加载 → 造实例 → 调 `call`"，卡在最后一步：**`call` 要的
`nlohmann::json*` 必须是插件那一版的对象**（`std::less<std::string>`，即
nlohmann < 3.11），我们手上是 3.11.2（`std::less<void>`），把我们的对象交给它
解引用就段错误。三条路：

1. 用插件那一版 nlohmann（试 3.9/3.10 的单头文件）编 harness，`json*` 就通了；
2. 跑现场宿主 `nclink-service`（它自己那版 json，天然对齐）——已试到中途：
   - ✅ 它能在 armv7 容器里起来；spdlog 报的
     `Failed getting file size from fd: Value too large for defined data type`
     是 32 位进程 `fstat()` 一个 Windows bind-mount 上的文件报 EOVERFLOW，
     把工作目录与日志放进容器自己的文件系统就好了；
   - ✅ `./nclink.cfg`（`-C nclink_cfg.json` 之外的老键值配置）的键名从二进制里
     抄出来了：`server_ip` / `server_port` / `reconnect_sec` / `user_name` /
     `password` / `log_level` / `log_file` / `log_limit` / `model` / `device_id`
     / 各主题的 `_qos`。空文件会让它 SIGBUS（读 0 字节文件），写全就不报打开了；
   - ❌ 之后仍是 qemu 下的 SIGBUS，崩得很早、日志一个字没写，这条路暂时不通。
3. 绕开 json：只调接受 JSON **文本**的入口（如
   `GSKHTTP::GSKHTTP(spdlog::logger*, std::string)`），但那样走不到业务逻辑。

任一条通了，GSK / KEDE / Mitsubishi-HTTP / 相机的设备侧请求形状就能在本地补齐。

### 6.4 网关路线：走通了（2026-09）🟢

上面第 2 条走不通，但换个对象就通了：**协议实现其实在 Go 网关里**。现场那台
`hp2x_box200`（:33123，"Communication Protocol Server"）自己实现各品牌协议，
C++ 插件只是 NC-Link 侧的适配器（它 POST 回网关）。而网关是**静态 Go 二进制**
——没有 C++ ABI 这回事，直接跑就行：

```sh
docker run --rm --platform linux/arm/v7 \
    -v <现场包>/app1/hp2x:/hp2x:ro -v tools/site-probe:/work \
    ncl-arm-probe sh /work/gateway_probe.sh
```

脚本做三件事：起一个假机床（`mock.py`，只记录）→ 起 `hp2x_box200` →
`POST /GSK/CNC/Open/TCP {"ipAddress":"127.0.0.1","port":6000,"timeout":5}`
拿到 `connectionId`，再逐项 `POST /GSK/CNC/<项> {"connectionId": …}`。
**设备侧请求就落在假机床的日志里**，一项一帧。

已经抓到 **GSK 的 11 条设备侧请求帧**（`STATUS` `0x11`、`PART_COUNT` `0x16`、
`PROGRAM` `0x12`、`LINE_NUMBER` `0x23`、`TOOL_NUMBER` `0x17`、`WARNING` `0x81`、
`0x1a`+子码的进给/主轴/倍率五条；帧头 `93`、帧尾 `55 aa`），见
[08 册 §4.5](08-GSK-广州数控.md)。

**同一套办法对其它自研模块都成立**（改一下模块名与项键即可）：科德
`/KEDE/CNC/GNC62/*`、三菱 `/Mitsubishi/CNC/M70/*`、三菱 PLC
`/Mitsubishi/Plc/MC/*`、西门子 `/S7/*`、Modbus `/Modbus/*`、FANUC `/FOCAS/*`、
840D `/SINUMERIK/*`… 这等于把"设备侧请求形状"这一格的抓取工作变成了
**改个模块名跑一遍**。

还差的一小格：**应答格式**。把请求原样回给网关会被判
`unexpected response command`，说明应答里的"命令"要按它的规则构造；用同一个
脚本（`gateway_probe.sh <应答hex>`）迭代即可，网关的报错就是判据。

## 7 落地顺序建议

1. **先补数据面**（零风险、纯抄）：把 §4 的模型项与 §4.3 的项键并进 08/09/20/24/25
   等分册，把 `driver_defs` 的端口/超时/路径分派并进我们的 `conf/driver/*.json` 样例。
2. **再补 SDK 型驱动**：FOCAS（01 册 + 29 个 `cnc_*`）、840D/i5（OPC UA 节点）、
   华数（Hsc3 API 面）——这三家可以按 SDK 的语义直接写，不依赖抓包。
3. **最后补自研 HTTP 三家**：按 §6 本地抓一次，把 URL/JSON 定下来。
